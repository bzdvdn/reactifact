    Рецепты¶

    reactifact.recipes — переиспользуемые строительные блоки, кодифицирующие паттерны, которые повторяются во всех демо. Импорт reactifact.recipes не тянет лишних зависимостей — всё построено на ядре.

    find / find_all — поиск типизированных артефактов в inputs¶

    Если агент объявляет больше одного типа в consumes, шаг получает плоский list[Artifact[Any]]; выбрать «тот самый Question» или «все Evidence» — почти в каждом шаге одна и та же строка next((a for a in inputs if isinstance(a.data, X)), None). find/find_all — типизированная замена в одну строку:

    from reactifact.recipes import find, find_all

question = find(inputs, Question)          # Artifact[Question] | None
evidence = find_all(inputs, Evidence)       # list[Artifact[Evidence]]

    search_sources / fan_out_sources — реактивный поиск¶

    search_sources — чистая часть: рассылает запрос и возвращает ранжированные refs, не трогая эффект-слот. Удобно, когда шаг сам создаёт артефакты и возвращает Emit:

    from reactifact import Emit
from reactifact.recipes import search_sources, source_ref_id

query = question.data.text
refs = await search_sources(context, query, owner_id=query_id, limit=5)
return [Emit(ref, id=source_ref_id(ref, query_id)) for ref in refs]

    fan_out_sources — обёртка над эффект-слотом: делает тот же поиск и пишет каждый ref как create-or-refresh артефакт. Передайте effects=, чтобы использовать явный слот вместо текущего produce.

    from reactifact.recipes import fan_out_sources

refs = await fan_out_sources(
    context,
    query=query,
    owner_id=query_id,           # скоуп рефов на владеющий ход
    limit=5,
    query_id=query_id,           # owner-ключ для провенанса
    on_start=lambda source: context.announce(
        f"Searching {source}…", kind="status"
    ),
    on_count=lambda source, n: context.announce(
        f"{source}: {n} hits", kind="status"
    ),
)

    Что делает:

    1. Рассылает запрос по всем настроенным источникам из context.resources.sources.
    2. Ранжирует объединённые SourceRef по скорам (сначала лучшие).
    3. Создаёт идемпотентные, скоупированные на владельца рефы (эффект Create): id=f"ref:{ref.stable_id()}:{owner_id}".

    Идемпотентность важна: поиск выполняется один раз за ход (свой маркер), но может повториться при ретраях — те же id пересоздаются без дублей. on_start / on_count дают прогресс-аннонсы поверх SSE.

    MemoryStore — namespaced-долговременная память (§27)¶

    from reactifact.recipes import MemoryStore

memory = MemoryStore(backend, namespace=f"user:{user_id}")
await memory.put(
    "tone",
    {"value": "concise"},
    text="prefers concise answers with citations",
    tags={"kind": "preference"},
    ttl_seconds=90 * 24 * 3600,
)
hits = await memory.search("how should answers be written?", k=3)

    Namespace обязателен (или задан на store), поэтому recall не прочитает чужого пользователя/workspace; tags фильтруют, ttl_seconds истекает на read/list/search, а search — детерминированный keyword-ranking (keyword_score, стемы/плюрализация) с подключаемым searcher(record, query) для семантики. forget() очищает namespace. Записи персистятся через любой KVBackend (file/SQLite/Postgres).

    Store — это межсессионный индекс, а не копия чата: сессии и чекипоинты остаются источником истины. remember_from(artifact, key=…) индексирует curated-артефакт (отчёт, предпочтение) и записывает source_session / source_artifact / source_version, поэтому запись можно пересобрать или удалить:

    record = await memory.remember_from(
    report,
    key=f"incident:{report.id}",
    source_session=session_id,          # явно: request/UserMsg/состояние приложения
    text=report.data.text[:800],
    tags={"kind": "report", "system": "k8s"},
)
assert record.source_artifact == report.id
removed = await memory.forget_source(record.source_session)   # GDPR-style

    source_session — обязательный явный аргумент: provenance это данные, а не ambient-состояние рантайма. Передайте сессию из запроса/артефакта пользователя или "", если запись не привязана к сессии; forget_source("") отклоняется, чтобы пустой ключ не удалил разом все записи без сессии.

    Если запись должна происходить после коммита артефакта, используйте outbox-форму из шага; рецепт сам формирует payload и dispatcher:

    memory.remember_after_commit(
    effects, report, key=f"incident:{report.id}", source_session=session_id
)
# app: Runtime(..., dispatcher=MemoryStore.dispatch)

    remember_after_commit записывает PendingAction; MemoryStore.dispatch находит зарегистрированный store в context.resources и вызывает put после коммита. Неизвестные kinds игнорируются, поэтому его можно комбинировать с другими dispatcher'ами.

    map_reduce — fan-out типизированных задач и reduce (§24)¶

    from reactifact.recipes import map_reduce

result = await map_reduce(
    context,
    items=docs,
    map_fn=lambda payload, index: summarize(payload),
    reduce_fn=lambda rows: merge(rows),
    key="summaries",
    concurrency=8,
    on_error="collect",
)

    Каждый item становится стабильным MapTask (map-task:{key}:{i}); worker превращает его в MapResult, а debounced ReduceStep срабатывает один раз, когда для ключа есть все результаты (map-reduced:{key}). on_error="collect" превращает упавший item в MapResult(error=...) и редьюсит остальные; "fail_fast" пробрасывает ошибку. Дочерний run имеет свой commit DAG (result.context), переиспользует tracer/budget родителя и пишет trace_metadata.parent_run_id.

    swarm — peer-to-peer handoff с защитой (§24)¶

    from reactifact.recipes import Handoff, swarm

result = await swarm(
    context,
    groups={"triage": triage, "billing": billing},
    start="triage",
    input=Question(text="refund please"),
    final_type=Answer,
    max_hops=6,
)

    Агент создаёт Handoff(to=..., reason=..., payload=...); helper запускает целевого агента от handoff, записывает hop как Handoff-артефакт со связью handoff_from к предыдущему шагу и останавливается на первом не-handoff выходе (связь derived_from). max_hops — жёсткий потолок; allow_repeat=False дополнительно запрещает повторный визит агента (SwarmCycle/SwarmLimit). Каждый hop — обычный subflow, поэтому trace/budget/provenance переносятся.

    materialize_doc — ленивое разрешение ссылок¶

    from reactifact.recipes import fan_out_sources, materialize_doc

# `as_artifacts=True` возвращает planned-Handle; materialize_doc их принимает
refs = await fan_out_sources(
    context, "gpu costs", owner_id="q1", as_artifacts=True
)
doc = await materialize_doc(
    context,
    refs[0],
    doc_type=TypedDoc,
    text_field="content",
    field_map={"path": "locator"},
)

    Короткая форма собирает документ из doc_type=: text_field получает содержимое, остальные поля заполняются из ref (locator, source_id, title, query_id, score, metadata). Для полного контроля остаётся фабрика:

    async def doc_from_ref(context, ref, content) -> TypedDoc:
    return TypedDoc(query_id=ref.data.query_id, path=..., content=content)

doc = await materialize_doc(
    context, refs[0], doc_from_ref, relation="resolved_from"
)

    materialize_doc принимает Artifact[SourceRef], обычный SourceRef или Handle из as_artifacts=True. Уже разрешённый resolved:{ref_id} документ переиспользуется с refresh=False (по умолчанию перечитывается, как раньше); отсутствие источника или сбой дают None и вызывают on_error(ref, exc), а не падение.

    Источники возвращают ссылки, а не содержимое, поэтому документы достаются лениво, только когда нужны — правило в демо research: «разрешить страницу только после того, как модель оценила её релевантной».

    Созданный документ связывается назад: TypedDoc ──resolved_from──► SourceRef, так что обход провенанса Answer → Claim → Evidence → Doc → SourceRef остаётся полным.

    StatusMachine — детерминированные жизненные циклы¶

    Машины состояний — паттерн для «артефакта, который проходит состояния» (исследовательский ход: researching → answerable → answered). Вместо ручного графа переходов StatusMachine — чистая функция текущего состояния:

    from reactifact.recipes import StatusMachine, StatusState


class EvaluateTurn(StatusMachine[ResearchTurn]):
    terminal = frozenset({"answered", "insufficient"}) # где останавливается
    query_id_field = "query_id"                        # owner-ключ (по умолчанию)
    status_field = "status"                            # поле статуса (по умолчанию)

    def next_status(self, state: StatusState[ResearchTurn]) -> str | None:
        """Чистая функция: какой статус жизненный цикл заслуживает сейчас."""
        if state.any(Answer):
            return "answered"
        return None

    def on_transition(self, context, key, old_status, new_status) -> None:
        context.announce(f"Research status: {old_status} → {new_status}",
                         kind="status", query_id=key)

    Для машины с одним методом StatusMachine.from_funcs(...) избегает subclass:

    machine = StatusMachine.from_funcs(
    artifact_type=ResearchTurn,
    terminal={"answered", "insufficient"},
    next_status=lambda state: "answered" if state.any(Answer) else None,
)

    Конструктор принимает те же опции: StatusMachine(artifact_type=..., next_status=..., terminal=..., consumes=...).

    Механика (всё унаследовано от Step):

    • Generic StatusMachine[ResearchTurn] задаёт artifact_type; явный artifact_type тоже работает.
    • По умолчанию будится любым событием; consumes= сужает набор событий. Событие сопоставляется с жизненным циклом через owner_key(artifact) (по умолчанию читает query_id_field данных артефакта с фолбэком на его id). Переопределите owner_key, если домен использует другой ключ; входы StatusState.inputs фильтруются тем же хуком.
    • Берёт последний подходящий артефакт artifact_type (по updated_at); terminal-статусы останавливают машину.
    • next_status получает типизированный StatusState[StatusT]: target плюс входы шага, уже отфильтрованные по key. state.status, state.all(T), state.any(T) и state.latest(T) заменяют повторяющийся list_artifacts(T) + проверку query_id == key.
    • next_status решает новый статус; None или отсутствие изменения ⇒ ничего не происходит.
    • Непосредственно перед применением вызывается on_transition(context, key, old_status, new_status) — ваш хук для прогресс-аннонсов.
    • Переход — это return-style Edit(target, **{status_field: new}), компилируемый в тот же update-effect; машина объявляет produces=(), потому что обновляет target, а не создаёт новый артефакт.

    Логику проверки кладите в отдельный шаг, реагирующий на смену статуса, — машина и верификатор разделены, детерминированы и тестируются по отдельности. EvaluateTurn в примерах knowledge/research — канонический образец этого рецепта.

    TurnContextStep — один контекст разговора на ход¶

    Transcript рендерит окно, но всё ещё принимает Context; TurnContextStep превращает типовой чат в один артефакт: текущий запрос, предыдущий запрос, ограниченную историю, rolling digest и флаг follow-up. Дальше шаги потребляют TurnContext и не собирают разговор заново.

    from reactifact.recipes.conversation import TurnFacts, TurnContextStep

def build_dialogue(facts: TurnFacts) -> DialogueContext:
    return DialogueContext(
        query_id=facts.trigger.id,
        history="\n".join(m.text for m in facts.history),
        prior_question=facts.previous_query or "",
        prior_answer=(
            facts.previous_answer.data.text
            if facts.previous_answer is not None
            else ""
        ),
    )

turn_context = TurnContextStep(
    UserQuery,
    assistant_type=Answer,
    digest_type=Digest,         # опционально; читает digest_id="digest"
    artifact_type=DialogueContext,  # цель custom build
    window=12,
    consume=OnCreate(UserQuery),    # или обычный Consume
    ensure=True,                    # идемпотентно на ход
    follow_up=my_follow_up,         # опционально; детерминированный дефолт
    build=build_dialogue,           # TurnFacts -> ваш артефакт
)

# groups=[turn_context, *answer_steps]

    Шаг создаёт TurnContext (или artifact_type=) с id turn:{trigger.id}; history ограничена текущим trigger'ом (более поздние ходы не попадают) и сохраняет поля turn/session_id. TurnFacts содержит trigger, текущий/предыдущий запрос, предыдущие artifact/answer, историю, digest и follow-up — поэтому доменный контекст может нести prior_domain/routing_text без чтения Context. consume=OnCreate — один артефакт на ход; ensure=True делает повторный запуск no-op. Комбинируйте с Annotated[..., Unscoped()], когда другому шагу тоже нужна полная история.

    WindowSummarizer — периодические чекпоинты диалога (§27, §37)¶

    Долгоживущая память чата — это просто состояние: артефакты-сообщения накапливаются, а саммарайзер сжимает недавнее окно каждые N сообщений в артефакт-чекпоинт. Рецепт владеет размером окна, периодичностью и идемпотентностью; домен владеет тем, как суммировать и как выглядит артефакт саммари:

    from reactifact.recipes import WindowSummarizer, llm_summarizer


class Summary(BaseModel):
    round: int
    text: str


def build_summary(round_no: int, text: str) -> Summary:
    return Summary(round=round_no, text=text)


class Flow(StepGroup):
    name = "chat"
    consumes = [Consume(Msg)]
    steps = [
        WindowSummarizer(
            Msg, Summary,
            summarize=llm_summarizer("Сожми недавний диалог в короткую заметку-память."),
            build=build_summary,
            window=8,   # сколько сообщений идёт в один саммари
            every=4,    # новый чекпоинт каждые N сообщений
        ),
    ]
    • summarize(context, history) -> str | None — ваш колбэк (или llm_summarizer(system=...) — тонкая обёртка над llm_reply); None запускает fallback рецепта (по умолчанию — обрезанная строка истории, никогда не падение).
    • build(round_no, text) -> Summary — форму артефакта саммари определяете вы; рецепт никогда не угадывает имена полей.
    • Id саммари выводится из количества сообщений (summary:{round} по умолчанию), поэтому повторный прогон того же поколения никогда не дублирует саммари. Батчевое создание обрабатывается: последний завершённый раунд создаётся, даже если несколько сообщений пришли за одну генерацию.
    • render/order_key/id_of переопределяемы, если дефолты (рендер по role/text, сортировка по created_at) не подходят вашему артефакту.
    • message_type также принимает последовательность типов (например, [UserQuery, Answer]), так что один чекпоинт покрывает гетерогенный поток.

    Не комбинируйте с WindowPruner. Cadence чекпоинтов считается по количеству сообщений, а prune останавливает рост этого счётчика, поэтому следующий чекпоинт не наступит. Если raw-окно должно быть ограничено (и при этом суммаризировано), используйте RollingDigestSummarizer; если нужен только ограниченный сырой транскрипт — WindowPruner сам по себе:

    from reactifact.recipes import WindowPruner

steps = [WindowPruner(Msg, keep=8)]

    WindowPruner полезен и сам по себе и принимает тот же один тип или последовательность типов.

    Рабочие кейсы — в tests/test_recipes_memory.py.

    RollingDigestSummarizer — одна растущая память вместо чекпоинтов по раундам (§27, §37)¶

    WindowSummarizer хранит снимок каждого раунда; но некоторым приложениям нужна одна память, которая накапливается сама, с небольшим сырым хвостом поверх. RollingDigestSummarizer — эта другая модель: как только диалог превышает trigger сообщений, всё, что старше window, сворачивается в один дайджест-артефакт — каждое сворачивание переписывает дайджест из предыдущего его текста плюс новых выпавших сообщений — а сами свёрнутые сообщения рецепт удаляет самостоятельно:

    from reactifact.recipes import RollingDigestSummarizer, llm_digest_summarizer


class Digest(BaseModel):
    text: str


def build_digest(text: str) -> Digest:
    return Digest(text=text)


class Flow(StepGroup):
    name = "chat"
    consumes = [Consume(Msg)]
    steps = [
        RollingDigestSummarizer(
            Msg, Digest,
            summarize=llm_digest_summarizer("Fold the new messages into the running memory note."),
            build=build_digest,
            window=8,    # сколько сообщений остаются сырыми
            trigger=12,  # порог длины диалога, после которого сворачиваем
        ),
    ]
    • message_type принимает как один тип, так и последовательность типов — например [Question, FinalResponse], если диалог собран из двух разных артефактов, а не одной модели Msg. Они объединяются и сортируются по order_key до того, как считаются window/trigger.
    • summarize(context, previous_digest_text, stale_artifacts) -> str | None получает выпавшие сообщения как сырой список артефактов, а не готовую строку — рецепт сам ничего не сплющивает в текст. Это важно, если у вас уже есть свой построитель role/content-промпта, или типы сообщений не сводятся к одной форме role/text: рендеринг пишете сами внутри summarize, и никакого round-trip через строковый формат рецепта не происходит. llm_digest_summarizer(system=...) — опциональный дефолт для тех, кому подходит обычный текстовый промпт: рендерит строками role: text (переопределяется через render=) и оформляет предыдущий дайджест и новую историю как две секции одного user-сообщения. None от любого из путей запускает fallback — по умолчанию он дописывает обрезанную строку истории к предыдущему дайджесту, а не отбрасывает его.
    • build(text) -> Digest — форму артефакта дайджеста определяете вы; digest_text — обратный читатель (по умолчанию artifact.data.text), если в вашей форме нет поля text.
    • Дайджест живёт под одним стабильным id (digest по умолчанию, digest_id) — каждое сворачивание обновляет его на месте, а не создаёт новый артефакт.
    • Не комбинируйте с WindowPruner: он удаляет без предварительного сворачивания, а значит теряет контент, который этот рецепт должен сохранить. Свой сырой хвост он ограничивает сам, ничего больше не нужно.

    llm_digest_summarizer и ChatMemory.from_transcript¶

    llm_digest_summarizer закрывает весь цикл «свернуть старые реплики в дайджест», включая fallback:

    from reactifact.recipes.conversation import MessageSpec, Transcript
from reactifact.recipes.memory import llm_digest_summarizer

transcript = Transcript([
    MessageSpec(UserQuery, "user"),
    MessageSpec(Answer, "assistant"),
])

summarize = llm_digest_summarizer(
    SUMMARY_SYSTEM,
    user=SUMMARY_USER,             # PromptTemplate с {previous}/{history}
    render=transcript.render,      # типизированные role-строки
    schema=AnswerBody,             # структурный вызов; без него — plain text
    max_fallback_chars=4000,
    attempts=1,
    temperature=0.2,
    max_tokens=800,
)
memory = ChatMemory.from_transcript(
    transcript,
    keep=settings.chat_memory_keep,
    summarize=summarize,
    summary_type=ConversationDigest,
    compact_commits=settings.chat_memory_commits,
)

    Колбэк возвращает предыдущий дайджест, если новой истории нет, не вызывает LLM при context.resources.llm is None, и откатывается на previous + "\n" + history (обрезанный), если провайдер бросил исключение, вернул None или пустой текст. fallback= переопределяет это поведение.

    Route — одна группа на значение артефакта¶

    Route — для частого случая «в ходе есть ключ ветвления; должна выполниться только одна downstream-группа». Это builder над обычными StepGroup, без вложенных групп в runtime. Каждая case-группа сохраняет свои шаги и поздние триггеры; сужаются только совпадения события on по key(value) == case.

    from reactifact.recipes import Route

route = Route(
    on=ResearchTurn,
    key=lambda turn: turn.domain,
    cases={
        "meta": kb_react_group,
        "rag": rag_group,
    },
    default="rag",       # значения вне map идут в rag
)

Runtime(ctx, groups=[*route.groups(), planner, ...])

    Сгенерированные группы несут route_case-маркер. validate_contracts использует его, чтобы не выдавать ambiguous_producer, если один артефакт производят разные case одной route; producer'ы вне route по-прежнему дают warning.

    ScopedCleanup — удалить scratch хода по scope¶

    EphemeralCleanup удаляет артефакты, id которых выводятся из ключа терминального артефакта. В чате id произвольные, но есть общий scope (query_id): ScopedCleanup реагирует на OnCreate(Answer) и удаляет все scratch-артефакты этого scope, не трогая другие ходы. В примере Answer — терминальный тип приложения.

    from reactifact import OnCreate
from reactifact.recipes.cleanup import ScopedCleanup

cleanup = ScopedCleanup(
    Answer,
    scratch_types=(DialogueContext, TurnIntent, ResearchTurn, Evidence),
    scope="query_id",          # или Scope(...)
    consume=OnCreate(Answer),  # дефолт
)

# groups=[create_step_group("cleanup", steps=[cleanup])]

    Он объявляет produces=() и реальные deletes=(...), поэтому контракты больше не утверждают, что cleanup создаёт Answer. related_all(type) фильтруется по ключу терминального артефакта; scratch-тип вне этого scope остаётся. scope обязателен (передайте None явно для намеренной глобальной очистки).

    run_tool_loop — ограниченный цикл native tool-calling (§46, §47)¶

    reactifact.tools.native намеренно даёт хелперы на один ход, а не цикл. Когда цикл всё-таки нужен — ограниченные раунды, параллельные вызовы, форсированный финальный ответ — run_tool_loop это opt-in рецепт, а не реактивный StepGroup:

    from reactifact.recipes import parse_tool_calls_with_textual, run_tool_loop

result = await run_tool_loop(
    call.context,
    system="You are a research assistant.",
    user=question,
    tools=[search_knowledge, read_source],
    mandatory="read_source",
    max_rounds=6,
    max_observation_chars=4_000,   # ограничить то, что уходит обратно в промпт
    redact_tool_outputs=True,      # применить resources.redactor к выводу тула
    parse_calls=parse_tool_calls_with_textual,  # терпеть DSML/XML-провайдеров
    on_event=lambda name, payload: ...,         # round/tool/final для SSE
)
call.effects.create(Answer(text=result.text))
    • Budget хода соблюдается между раундами: max_tool_calls ограничивает выполнения (лишние вызовы возвращаются как ошибки тулов), max_seconds и лимиты токенов/стоимости останавливают новые раунды; затем цикл форсирует ответ.
    • fallback(ctx, messages, text) вызывается, когда вызовов не распарсили, а текст похож на tool-call разметку (looks_like_tool_markup); верните строку, чтобы завершить ход (например, делегировать в legacy ToolUse), или None, чтобы принять текст как ответ.
    • on_event получает round_start, tool_call, tool_result, final; тот же прогресс публикуется через Context.announce(kind="agent"), поэтому Chat(status_kinds=("status", "agent")) стримит его без своего цикла.
    • ToolLoopResult.stop_reason — completed, max_rounds, budget, provider_error или fallback; error содержит детали отказа провайдера. Ошибки тулов тоже типизированы: ToolOutput.failed(ToolError(code=, message=, retryable=)) виден как ToolObservation.error_info, а retry_tool_errors=True повторяет только retryable=True (tool_retry_attempts/tool_retry_delay задают backoff; повторы считаются выполнениями для Budget.max_tool_calls).

    keyword_score / stem_words — детерминированный скоринг текста (§67)¶

    Там, где эмбеддинги опциональны, покрытие по ключевым словам — нейтральный фолбэк (английский чат knowledge и каталог repair используют именно его):

    from reactifact.recipes import EN_STOPWORDS, keyword_score, stem_words

keyword_score("How to set up authentication", "authentication")          # 1.0
keyword_score("Установка аутентификации", "аутентификацию", use_stems=True)  # 1.0
stem_words("Ремонт комнаты и kitchen")  # {"ремонт", "комнат", "kitchen"}
    • Английские стоп-слова убираются с обеих сторон по умолчанию (EN_STOPWORDS).
    • use_stems=True включает небольшой русский стеммер окончаний, поэтому «аутентификацию» совпадает с «аутентификация» без модели.

    Skills — инструкции, подгружаемые по ситуации (§67)¶

    Skill — тот же формат, что у Claude Skills: markdown-файл с фронтматтером name/description и телом процедурных инструкций. Это не Source — Source извлекается, чтобы ответить фактами; skill загружается, чтобы изменить как именно делается LLM-вызов текущего хода (правило, формат), когда его описание совпадает с ситуацией:

    from reactifact.recipes import load_skills, match_skills

# --- один раз, при старте ---
skills = load_skills("skills/")   # каждый *.md-файл, разобранный по фронтматтеру

# --- на каждом ходу, только там, где применимо ---
situation = "reporting an answer backed by a number computed from structured storage"
for skill in match_skills(skills, situation):
    prompt += f"\n\nInstruction ({skill.name}): {skill.body}"

    Файл skill:

    ---
name: cost-reporting
description: How to report a number computed from structured storage. Use when the answer is backed by a deterministic calculation.
---
State the exact computed value explicitly, and say plainly it was computed,
not estimated — name the source and column it came from.
    • situation — короткое описание происходящего, написанное кодом, не обязательно сырой вопрос пользователя: вызывающий код характеризует момент, так же как description самого skill характеризует, когда его применять. Это сохраняет триггер реактивным (§8): skill срабатывает из-за того, какое состояние существует (например, артефакт Calculation), а не потому что код разбирает формулировку пользователя.
    • Сопоставление — keyword_score (детерминированно, без эмбеддингов) по name + description; возвращаются только совпадения не ниже threshold (по умолчанию 0.34), не больше limit (по умолчанию 1) — skill должен быть точным триггером, а не фолбэком, срабатывающим на каждом ходу.
    • Это намеренно не новый core-примитив (§61): body подобранного skill — обычная строка, которую вы добавляете в промпт structured_llm/ llm_reply. Skill cost-reporting из демо knowledge (examples/knowledge/skills/) — канонический пример — см. его README (на английском).
    • Границы: здесь реализована инструкционная половина формата Claude Skills — frontmatter + процедурный markdown. Вторая половина — бандл исполняемых скриптов, которые skill может нести с собой и которые модель запускает — не реализована. Это осознанная граница, а не пробел для закрытия: выполнение кода skill'а самой моделью — это вопрос sandboxing и прав доступа, а детерминизм reactifact (§67) как раз про то, чтобы не отдавать раннтайму на исполнение непроверенный код. Если это нужно — оформите скрипт как Tool сами (§46): его можно достать из body совпавшего skill (назвать в инструкции) или использовать независимо.

    PlanExecute — последовательный plan → execute → finish (§24, §42, §69)¶

    Plan-and-Execute (в духе LangChain/AutoGPT): план строится один раз, его шаги выполняются строго по одному, каждый гейтится на результат предыдущего, а финальный ответ синтезируется, когда результат есть у всех шагов. Портировано из ручных Planner/Executor/Finisher в reactifact.recipes.PlanExecute (141 + 14 строк), обобщено: рецепт владеет порядком, гейтингом, идемпотентным re-entry и детекцией завершения; вы реализуете только три решения, которые реально требуют суждения.

    from reactifact.recipes import PlanExecute


class Flow(PlanExecute[Goal, PlanStep, StepResult, FinalAnswer]):
    goal_type = Goal
    step_type = PlanStep
    result_type = StepResult
    final_type = FinalAnswer

    async def plan(self, context, goal) -> list[PlanStep]:
        ...  # упорядоченные шаги — index/goal проставляет рецепт

    async def execute_step(self, context, step, history) -> StepResult:
        ...  # history: результаты всех предыдущих шагов по порядку

    async def finish(self, context, goal, results) -> FinalAnswer:
        ...  # собрать результаты всех шагов по порядку


class FlowAgent(StepGroup):
    consumes = [Consume(Goal), Consume(PlanStep), Consume(StepResult)]
    steps = Flow().produces()

    Тот же поток без подкласса — и с автоматической сборкой группы/пайплайна:

    from reactifact.recipes import PlanExecute

flow = PlanExecute.from_funcs(
    goal_type=Goal,
    step_type=PlanStep,
    result_type=StepResult,
    final_type=FinalAnswer,
    plan=plan,                    # sync или async
    execute_step=execute_step,
    finish=finish,
)
pipeline = flow.pipeline(seed_type=Goal)   # или flow.group() в Runtime
result = pipeline.run(Goal(text="ship it"))
    • step_type/result_type должны нести поля goal_field/index_field (по умолчанию "goal"/"index") со значениями по умолчанию (например, index: int = 0) — рецепт сам проставляет реальные значения при каждом create, в хуках их заполнять не нужно.
    • Поддерживает несколько целей одновременно в одном Context — шаги/ результаты скоупятся по goal_field, а не «что сейчас лежит в Context».
    • Провенанс: финальный артефакт линкуется supported_by → на каждый результат шага (§34).

    Рабочие кейсы — tests/test_recipe_plan_execute.py.

    Router / ApprovalGate — классификация, затем подтверждение перед финализацией (§60, §67)¶

    Два независимых элемента: роутер и approval gate; паттерн повторяет ручные RouteTask/Supervisor:

    • Router — классифицирует запрос в один из фиксированного набора маршрутов, идемпотентно, с детерминированным fallback, когда вызов классификации недоступен или вернул что-то вне routes (§67).
    • ApprovalGate — просит человека подтвердить отчёт перед финализацией (§60). Отслеживает всю историю approval-вопросов треда, а не только неотвеченные — иначе повторный вход после отказа заводит дублирующую цепочку вопросов; именно эту ошибку рецепт и не даёт написать снова. Использует kind="approve" — тот же вокабуляр, что и gate деструктивных инструментов (reactifact.tools.use) и Verify (verify.py), так что один control-plane UI для "approve"-запросов покрывает все три источника.
    from reactifact.recipes import ApprovalGate, Router


class MyRouter(Router[Request, Task]):
    request_type = Request
    task_type = Task
    routes = ("budget", "timeline", "quality")

    async def classify(self, context, request) -> str | None:
        ...  # структурное LLM-решение, или None для fallback

    def fallback_route(self, context, request) -> str:
        ...  # детерминированное совпадение по ключевым словам и т.п.


class MyGate(ApprovalGate[SpecialistReport, FinalReply]):
    report_type = SpecialistReport
    final_type = FinalReply

    def approval_question(self, context, report) -> str: ...
    async def on_approve(self, context, report) -> FinalReply: ...
    async def on_reject(self, context, report, answer) -> FinalReply: ...


class Flow(StepGroup):
    consumes = [Consume(Request), Consume(Task), Consume(SpecialistReport),
                Consume(PendingQuestion)]
    steps = [MyRouter().produce(), Specialist(), MyGate().produce(),
             Step(PendingQuestion)]  # Router/ApprovalGate зовут human.ask в runtime

    Specialist — собственно работа маршрута — остаётся полностью вашим Step; в «что делает маршрут» нет ничего обобщаемого.

    ReflectionLoop — генерация → критика → перегенерация (§24, §42, §69)¶

    Паттерн "Reflection" из LangGraph, портирован из ручных DraftIt/Critic/Rewrite/Finalize в reactifact.recipes.ReflectionLoop. В отличие от PlanExecute (неизменяемые, индексированные шаги), рабочее состояние здесь — один мутируемый артефакт черновика на тему, обновляемый на месте каждый раунд — как и в портируемом примере (effects.update(draft, ...)).

    from reactifact.recipes import ReflectionLoop


class MyLoop(ReflectionLoop[Topic, Draft, Review, Final]):
    topic_type = Topic
    draft_type = Draft
    review_type = Review
    final_type = Final
    accept_at = 0.8
    max_rounds = 2

    async def draft(self, context, topic) -> Draft: ...
    async def critique(self, context, draft) -> tuple[float, str]: ...  # (score, feedback)
    async def rewrite(self, context, draft, feedback) -> Draft: ...
    async def finish(self, context, draft) -> Final: ...


class Flow(StepGroup):
    consumes = [Consume(Topic), Consume(Draft), Consume(Review)]
    steps = MyLoop().produces()

    То же самое функциями:

    loop = ReflectionLoop.from_funcs(
    topic_type=Topic,
    draft_type=Draft,
    review_type=Review,
    final_type=Final,
    draft=draft,
    critique=critique,            # (score, feedback), sync или async
    rewrite=rewrite,
    finish=finish,
    accept_at=0.85,
)
pipeline = loop.pipeline(seed_type=Topic)
    • draft_type должен нести topic_field/round_field/status_field (по умолчанию "topic"/"round"/"status"); review_type тоже должен нести topic_field — до Review рецепт добирается только реагируя на создание самого Review, поэтому тему нужно прочитать прямо с него. Дайте этим полям значения по умолчанию — рецепт проставит реальные значения при каждом create/update.
    • Ограничение раундов (max_rounds) и порог принятия (accept_at) — на стороне рецепта, а не разбросанные по трём produce проверки вида if round + 1 > MAX_ROUNDS.
    • Поддерживает несколько тем одновременно в одном Context.

    Рабочие кейсы — tests/test_recipe_reflection.py.

    changed_fields / earliest_stage / downstream_fields — «изменить → пересобрать»¶

    Длинные многоэтапные потоки иногда должны откатываться: пользователь правит факт, пайплайн пересобирается с самой ранней затронутой стадии и очищает всё ниже по потоку. Хелперы общие; ваш — это карта field_stages и порядок стадий (одобрение в repair — канонический пример):

    from reactifact.recipes import changed_fields, downstream_fields, earliest_stage

field_stages = {"room": "collect", "style": "design_choice",
                "area": "plan", "budget": "estimate"}
order = ("collect", "design_choice", "plan", "estimate")

changed = changed_fields(old_info, new_info)          # {"style", "budget"}
target = earliest_stage(changed, field_stages=field_stages, order=order)
reset = downstream_fields(target, field_stages=field_stages, order=order)

    changed_fields игнорирует поля, которые в новом состоянии остались None (модель не знала); earliest_stage возвращает None, если ничего не изменилось; downstream_fields включает саму цель (всё на этой стадии и позже сбрасывается, выше по потоку — сохраняется).
