# Устойчивость и resume

reactifact — однопроцессный рантайм без брокера, но **прогон на сессии
переживает рестарт процесса**: откройте сессию заново и продолжайте, вместо
того чтобы терять работу, которую прерванный прогон поставил в очередь. Ниже
— что именно гарантируется, а что нет.

## Что сохраняется

`SessionStore` сохраняет весь `Context` (`Context.to_dict`) под `session_id`:

- **артефакты** (типизированные, версионированные) и **связи** между ними;
- **цепочку коммитов** (`Context.history()`), так что провенанс и `diff`/
  `rollback`/`replay` продолжают работать;
- **очередь отложенных триггеров** — события, которые ещё не разослало ни одно
  поколение.

При дефолтном `session_save_policy="per_commit"` рантайм сохраняется на каждой
**границе поколения**, *после* того как батч триггеров этого поколения
израсходован. Поэтому снапшот консистентен: уже израсходованный триггер не
реплеится, а тот, чей consumer так и не запускался, — остаётся.

```python
from reactifact import Runtime, SessionStore
from reactifact.checkpoints import SQLiteKVBackend

store = SessionStore(SQLiteKVBackend("sessions.sqlite3"))
session = await store.open("user-1")            # загружает или создаёт
runtime = Runtime(session.context, agents=[...], session=session)
await runtime.arun()
```

```text
# после краха / рестарта — новый процесс, в памяти ничего нет
session = await store.open("user-1")
runtime = Runtime(session.context, agents=[...], session=session)
await runtime.arun()   # продолжает: отложенные триггеры на месте
```

Таким образом прерванный прогон возобновляется с **последнего
закоммиченного поколения**, а любой поставленный в очередь, но ещё не
обработанный триггер рассылается снова.

## Гарантия: at-least-once

Возобновление — **at-least-once**, а не exactly-once. Produce, который уже
закоммитился до краха, может выполниться снова. Если он не идемпотентен, это
даст дубликат артефакта (или повторный внешний side effect).

Давайте produce **stable id**, чтобы повторный прогон делал upsert, а не
дублировал ([§42](../constitution.md)):

```python
@produce(Summary)
async def summarize(call):
    doc = call.trigger
    # Stable id делает повтор идемпотентным: повторное создание вернёт тот же
    # артефакт и не породит второго события.
    call.effects.create(Summary(text=...), id=f"summary:{doc.data.url}")
```

`effects.create_once_from(...)` (stable id, выведенный из триггера) и
`Consume(..., debounce=True)` — остальные инструменты для той же цели.

## Что **не** покрывается

- **Внешние side effects.** Письмо, запись файла, вызов стороннего API внутри
  produce могут повториться при retry. Фреймворк не может сделать их
  exactly-once — защищайте своим идемпотентным ключом. (`call.request` доступен
  для correlation id; см. `reactifact.request`.)
- **Работа «в полёте».** Produce, который выполнялся в момент краха, просто
  перезапускается; durable — только закоммиченные поколения.
- **Бюджеты сбрасываются на прогон.** Счётчики `Budget` (`max_runs`,
  `max_seconds`) живут в рамках одного вызова `arun()`; возобновление начинает
  свежий бюджет, а не остаток старого.
- **Гранулярность `per_turn`.** При `session_save_policy="per_turn"` сессия
  сохраняется один раз в конце хода, поэтому крах посреди хода откатывает весь
  ход и перезапускает его. `per_commit` (дефолт) сохраняется на каждой границе
  поколения.

## Resume vs. replay

Две разные операции, которые часто путают:

- **Resume** (`session.open(...)` + `Runtime.arun()`) продолжает *прерванный*
  прогон: рассылает отложенные триггеры заново и может перезапустить produce.
- **Replay** (`reactifact replay`, `ReplayLLM`) восстанавливает *почему
  завершённый прогон пришёл к своему состоянию* — детерминированно, без
  перезапуска агентов; см. [Replay](replay.md).

Первое — исполнение, второе — аудит.
